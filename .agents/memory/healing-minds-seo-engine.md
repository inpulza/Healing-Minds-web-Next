# Healing Minds SEO Publishing Engine

Long-running, intermittent project. Healing Minds is the **second pilot** for turning XL Homes' SEO editorial system into a packageable module reusable for any Inpulza client/niche. Goal is NOT to copy-paste XL Homes' blog — it's to **adapt** the proven methodology to a healthcare/YMYL context, step by step (no big bang).

## What XL Homes already has (the reference system)
- Admin panel to create/generate blogs.
- Editorial flow with many steps: idea → research → anti-cannibalization → article → SEO metadata → images → verification → publish.
- Public blog rendered for Google, dynamic sitemap.
- Post-publish SEO hook: audits the URL (canonical/robots/content/sitemap), submits sitemap to Search Console, runs URL Inspection.
- Proven in production on xl-homes.com.

## Healthcare-specific constraints (non-negotiable, this is YMYL)
- Responsible medical tone; reliable/credible sources.
- Careful with clinical claims; add disclaimers where applicable.
- **Human review before publishing** (draft → human review → publish).
- Bilingual EN/ES routes when it makes sense.
- Local focus: Naples, Southwest Florida, telepsychiatry Florida.

## Reviewing CodeX PRs from this Repl (access method)
- The GitHub repo `inpulza/Healing-Minds-Psychiatry-New-Web` is **private**; CodeX pushes branches and opens PRs there. CodeX's code does NOT auto-arrive in this Repl's workspace — it stays on `main` until pulled.
- Main agent's shell has **no GitHub credential by default** (no credential helper, no token) — git ops to `origin` fail with "Authentication failed". A user-provided `GITHUB_TOKEN` secret unlocks access.
- **`git fetch`/`git checkout` are BLOCKED for the main agent** (treated as destructive). So you cannot fetch the PR branch into `.git`. Instead, read the PR via the **GitHub REST API** (`api.github.com` is reachable): use `GITHUB_TOKEN` to GET `/repos/.../pulls/N` (diff media type `application/vnd.github.v3.diff` for full diff), `/pulls/N/files`, etc.
- You can't run the PR branch's npm scripts without the files in-workspace. Two ways to actually run them: (a) have the user pull the branch via Replit's Git pane (UI has the OAuth token), or (b) replicate the logic against the live production site (the SEO audit just fetches public URLs over HTTP).
- Never print the token, and never put it in a remote URL or anywhere in `argv` (it survives in the reflog, the process list and error messages). For git over HTTP use the inline credential helper (`git -c credential.helper='!f(){ echo username=x-access-token; echo password=$GITHUB_TOKEN; };f' ...`); for the REST API send `Authorization: Bearer` from the environment variable. Redact any echoed output.

## Production DB is SEPARATE from dev (deploy gotcha — hard-won)
Verified via read-only prod query: production runs a **different** database than the dev
workspace (prod has only the old `users`/`contact_messages`; new tables created by
`db:push` in dev do NOT exist in prod). On **Publish**, Replit auto-migrates the *schema*
dev→prod (creates the new tables) — but it does **NOT** copy *data*. So any seed/content
lives only in dev until something writes it to prod.
**Why:** the agent's prod access (`executeSql environment:"production"`) is READ-ONLY, and
the prod connection string isn't exposed in dev — so the agent cannot seed prod directly,
and must not write custom prod-migration/seed scripts or deploy hooks (Replit owns prod schema).
**How to apply:** before declaring a feature "live in prod", confirm prod has the needed
DATA, not just schema. Options to seed prod: (a) CodeX adds an idempotent seed-on-boot in the
compiled server, or (b) bake an idempotent seed into the deploy run command (risk: dev-only
tools like `tsx` may be absent in prod). Decide WITH the user before deploying — empty prod
content silently fails smoke tests that expect specific URLs to load.
**RESOLVED (Sprint 2.5)** via option (a): the compiled server runs an idempotent seed at boot.
Two non-negotiable safety rules learned here: (1) the seed call MUST be wrapped in try/catch at
the startup site so a seed failure logs but NEVER blocks server start — otherwise the whole site
goes down, not just the blog; (2) inserts MUST use onConflictDoNothing + re-read, because
autoscale boots multiple instances concurrently and getOrCreate (select-then-insert) races on the
unique (language,slug) index. A toggle (BLOG_SEED_ON_BOOT=false) lets prod disable it later.

## Evidencia de cutover: qué puede exigir un guard de arranque

Un guard que solo comprueba "existe una fila con esta clave" no prueba nada cuando las claves de idempotencia las elige quien llama a la API: hay que **reservar la clave en el código** (rechazo 400 en el único embudo de creación de runs) y **validar la firma completa** de la fila: pase completo, empezado desde el principio, sin fallos y con totales.

**Why:** la fila que sirve de evidencia vive en la misma tabla que las auditorías normales, y la ruta de auditoría acepta `idempotencyKey` del cliente.

**How to apply:** completitud → rehusar el arranque; frescura (posts editados después del último backfill completo) → **aviso, nunca fatal**. Bloquear el arranque porque alguien editó un post convierte un problema de datos en una caída, y el resto del pipeline de enlaces falla en abierto a propósito.

## Freshness windows start at the start of the pass

Comparing content `updated_at` against a batch run's `completed_at` misses edits made during the
run: a post edited after its own batch was processed still has a timestamp older than the run's
completion, so it looks scanned when nothing rescanned it. Compare against `started_at`.

**Why:** the window between "your batch was processed" and "the pass finished" is exactly where an
edit hides, and the whole point of the check is to notice unscanned content.

**How to apply:** `updated_at > coalesce(started_at, completed_at)`. It can only over-report, which
is the right direction for a warning that must never block startup — completeness refuses to boot,
freshness only warns.
